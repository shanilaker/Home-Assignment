# חנות קטנה - מערכת הזמנות מינימלית (Python)

מערכת Web מינימלית לעסק קטן שמוכר מוצרים: לקוח רואה מוצרים (מגיעים מ-DB), בוחר מוצר ומבצע הזמנה שנשמרת ב-DB, וצד העסק יכול לצפות בהזמנות שנוצרו.

- **URL ציבורי** -Render: **https://home-assignment-uc6u.onrender.com**
- **GitHub repo:** https://github.com/shanilaker/Home-Assignment

## סטאק טכנולוגי

- **Backend + Frontend:** Python, FastAPI, עם דפי HTML מוגשים בשרת (Jinja2 templates) - אין JavaScript בצד לקוח.
- **Database:** Supabase (Postgres), דרך הספרייה הרשמית `supabase-py`.
- **Deployment:** Render (Web Service מחובר ל-GitHub, deploy אוטומטי מ-main).

בהתחלה שקלתי frontend סטטי (HTML/JS מדבר ישירות מול Supabase, בלי backend) בגלל שהוא הכי מהיר לפריסה. בחרתי בסוף ב-Python/FastAPI במקום זאת, כדי שאוכל להבין ולהסביר כל שורת קוד לעומק - חשבתי שזה שווה את הזמן הנוסף בהתחשב בכך שחלק מהמטרה של התרגיל היא היכולת להסביר את ההחלטות שלי.

## איך מריצים מקומית

1. יוצרים סביבה וירטואלית ומתקינים תלויות: `pip install -r requirements.txt`
2. מעתיקים `.env.example` ל-`.env` וממלאים בו את `SUPABASE_URL` ו-`SUPABASE_KEY`.
3. מריצים את `schema.sql` בלשונית ה-SQL Editor בפרויקט ה-Supabase (פעם אחת - יוצר טבלאות, RLS, seed data, ופונקציית `place_order`).
4. מריצים את השרת: `uvicorn main:app --reload`
5. פותחים בדפדפן: http://127.0.0.1:8000

## מבנה הפרויקט

```
main.py             - FastAPI app: routes ל-/, /order, /orders
templates/          - דפי Jinja2 (index.html, orders.html)
static/styles.css   - עיצוב משותף
schema.sql          - סכמת ה-DB, RLS policies, seed data, ופונקציית place_order
requirements.txt    - תלויות Python
.env.example        - תבנית למשתני הסביבה הנדרשים
```

## דרישה נוספת שנבחרה: ניהול מלאי (Stock)

כל מוצר כולל שדה `stock`. הזמנה חדשה עוברת דרך פונקציית Postgres בשם `place_order` (ב-`schema.sql`) שבודקת את המלאי הזמין, מקטינה אותו, ויוצרת את ההזמנה - הכל בטרנזקציה אטומית אחת (עם `SELECT ... FOR UPDATE` שנועל את השורה), כדי למנוע overselling כששני לקוחות מזמינים בו-זמנית את הפריט האחרון.

## החלטות מרכזיות

- **FastAPI + Jinja2 (server-rendered), בלי JS** - כדי שכל הקוד יהיה בפייתון, שפה שמאפשרת לי להבין ולהסביר כל שורה, במקום frontend סטטי שהיה מהיר יותר לפרוס אבל פחות מובן לי.
- **ניהול מלאי דרך RPC אטומי בפוסטגרס** ולא בקוד השרת - כדי למנוע race condition בין בקשות מקבילות (שני לקוחות שמזמינים את אותו פריט בו-זמנית).
- **קריאת orders ציבורית** (ללא הזדהות) - פישוט מכוון לצורך הזמן הנתון. בסביבת אמת הייתי מוסיף הזדהות (Supabase Auth) לעמוד `/orders` כדי שרק בעל העסק יראה אותו.
- **Render לפריסה** - תמיכה טבעית בשרתי Python, אינטגרציה פשוטה עם GitHub, deploy אוטומטי מכל push.
- **טופס הזמנה נפרד לכל מוצר** (במקום שדה שם/טלפון משותף אחד) - פשוט יותר למימוש ב-server-rendered HTML בלי JS.

## מה עובד

- הצגת כל המוצרים מה-DB בעמוד הבית, כולל מחיר ומלאי בזמן אמת.
- ביצוע הזמנה: בדיקת מלאי, הקטנתו, ושמירת ההזמנה - הכל אטומי דרך פונקציית `place_order`.
- מניעת הזמנה כשאזל המלאי (הכפתור מושבת ומוצג "אזל מהמלאי").
- עמוד `/orders` המציג את כל ההזמנות שהתקבלו, ממוין מהחדש לישן, כולל שם המוצר.
- המערכת פרוסה וזמינה ב-URL ציבורי, מחוברת ל-GitHub עם deploy אוטומטי.

## מה לא הושלם

- אין הזדהות/הרשאות על עמוד `/orders` - כרגע כל מי שיש לו את הקישור יכול לצפות בהזמנות.
- אין ולידציה מתקדמת על מספרי טלפון או שדות קלט (רק `required` בסיסי של HTML).
- אין בדיקות אוטומטיות (unit/integration tests).
- אין ניהול תמונות מוצר.
- הודעת שגיאה כשההזמנה נכשלת (למשל מלאי לא מספיק) מוצגת כטקסט גולמי מה-DB ולא מנוסחת בצורה ידידותית למשתמש.

## מה הייתי עושה עם עוד שעה

- מוסיפה הזדהות בסיסית (Supabase Auth) לעמוד ההזמנות של העסק.
- משפרת הודעות שגיאה למשתמש (ניסוח ידידותי במקום טקסט שגיאה גולמי).
- מוסיפה בדיקות אוטומטיות בסיסיות (pytest) לפונקציית ההזמנה.
- נועלת (pin) גרסאות מדויקות ב-`requirements.txt` - נתקלתי בבאג תאימות בין גרסאות Starlette/Jinja2 (`TypeError: unhashable type: 'dict'`) שהיה נחסך אם הגרסאות היו נעולות מראש.
- מוסיפה תמונות מוצר ועיצוב responsive משופר יותר למובייל.
